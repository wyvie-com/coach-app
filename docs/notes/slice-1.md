# Slice 1: Hevy client (read-only)

Date: 2026-10-05. Branch `claude/funny-cori-evrx1v`.

## What was built

- `coach.hevy.models`: Pydantic models for the raw shapes (`WorkoutsPage`, `RawWorkout`, `RawExercise`, `RawSet`, `WorkoutCount`). Strict on the fields the figures depend on: ids, `start_time` and `end_time` as timezone-aware datetimes (a naive string is rejected), exercise `title` and `exercise_template_id`, set `type`, `weight_kg`, `reps` (integer; `5.5` is rejected) and `rpe`. Everything else is kept through `extra="allow"`, so a new Hevy field never breaks a pull.
- `coach.hevy.client.HevyClient`: page iteration over `GET /v1/workouts` with `pageSize=10` (the documented maximum), stopping at `page_count`; a 0.5 s polite interval between pages; bounded retries (5 attempts) on 429 and 5xx and on transport errors, with exponential backoff 1, 2, 4, 8 s capped at 30 s, honouring `Retry-After` when present (capped at 60 s); 401 raised at once as `HevyAuthError` with a message naming the route; other 4xx raised as `HevyError` with the status and never the body. Returns `FetchedPage(page, raw)` so the caller can store the body exactly as received.
- `coach.hevy.store.PullStore`: writes `private/hevy/<YYYY-MM-DD>/page-NNN.json` verbatim and a `manifest.json` of counts (`pulled_on, route, docs_date, page_size, pages, workouts, workout_count`); reads pages back in order; finds the latest pull date.
- `coach.hevy.pull` and `coach pull [--root] [--page-size]`: count, then every page, then the manifest. Prints five lines: route, workout count, pages, workouts stored, directory.
- Fixtures under `tests/fixtures/hevy/`: generated by `make_fixtures.py` (committed, so their synthetic origin is checkable), three pages of two workouts, a count, and two malformed pages. `README.md` records the docs date (2026-10-05) and the field list.
- `tests/conftest.py` makes `socket.getaddrinfo` raise in every test, so "no network in tests" is enforced rather than assumed.
- Tests: 22 new, 40 in total. Pagination over three pages (page numbers, `pageSize`, header on every request, interval slept exactly twice, raw body preserved); page-number mismatch; 429 with `Retry-After` honoured; 5xx backoff sequence; bounded attempts; transport errors; 401 on each route with the key absent from the message; 401 never retried; 4xx without body; malformed page; store round trip and manifest contents; the pull summary containing no set data.

## Live dry run

`uv run coach pull` against my account, 2026-10-05:

```
route           proxy
workout_count   611
pages           62
workouts        611
directory       private/hevy/2026-10-05
```

45 seconds wall clock for 63 requests. The stored pages carry exactly the documented keys at every level (`page, page_count, workouts`; nine workout keys; six exercise keys; eight set keys). One difference from the docs examples: Hevy sends timestamps with a `+00:00` offset rather than `Z` (**Secondary**, observed; both are valid ISO 8601 and both pass the aware-datetime rule). `git status` shows nothing under `private/`.

## Decisions and rejected alternatives

- **Store the raw body, not the parsed model.** The first version wrote `model_dump()`, which re-serialises timestamps and would drop nothing today but is not what Hevy sent. Changed to carry the decoded body alongside the validated page. The test asserts the stored page equals the fixture.
- **Page-number pagination, not `/v1/workouts/events`.** The events endpoint is for incremental sync; a full pull of 62 pages takes 45 seconds and is simpler to reason about for a weekly job. Incremental sync is in `docs/later.md`.
- **No documented rate limit, so a fixed interval.** The OpenAPI document has no limit, no 429 and no `Retry-After`; its one request is not to run on the hour. 0.5 s between pages is polite without doubling the pull time. `Retry-After` is honoured anyway in case Hevy adds one.
- **401 is never retried.** Retrying an auth failure cannot succeed and would hide the real problem behind backoff delays.
- **Error messages carry status and path, never the body.** A body could contain anything; the one documented 400 body (`{"error": ...}`) is not needed to act.
- **Injected `sleep` and `transport`.** Tests assert the exact backoff sequence without waiting, and the production path is the same code with defaults. Rejected: mocking `time.sleep` globally, which couples tests to an implementation detail.
- **`reps` as `int`, `type` as `str`.** Reps cannot be fractional, so a fractional value is a data error worth failing on. Set type is prose in the read schema, so unknown values are kept and mapped to `other` in slice 2 rather than rejected here.

## What it does not do yet

No internal model, no figures, no exercise templates (`/v1/exercise_templates` is not needed while titles and template ids come with each workout). No incremental sync. No `coach figures`.

## Three questions an interviewer might ask

1. Why keep both the validated model and the raw body instead of one or the other? The model is what the code is allowed to depend on; the raw body is what can be recomputed from later if the model turns out to be wrong or Hevy changes. Storing only the model would silently lose any field the model ignores, and storing only the body would push validation to every reader.
2. Hevy documents no rate limit. What does the client do and why is that defensible? A fixed 0.5 s interval between pages, bounded retries with exponential backoff on 429 and 5xx, and `Retry-After` honoured if it ever appears. The interval is a courtesy to an undocumented service; the retries bound the cost of a bad day; and the docs' only request, not to run on the hour, is a scheduling rule the live-run procedure follows.
3. Why is 401 treated differently from the other 4xx codes? Because on the proxy route it has a specific meaning: the platform did not inject the header. The message says so, names the route, and never includes the header value, so the person reading it knows whether to configure the proxy or fix a key. Retrying would only add delay.
